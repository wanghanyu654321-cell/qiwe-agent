## 场景证据

| 范围 | 可观察结果及边界 |
| --- | --- |
| 多成员 | A/B同店、C另一店，独立可信成员读取器和授权对象，多连接共享真实SQLite/工件目录。本人报数、确认及更正金额正确；同店manager汇总330元，另一店390元，跨成员报告及任务拒绝访问 |
| 文件 | 同店同版本的两个owner分别导出真实XLSX，字节一致、收件人各自固定；跨店不能读取或上传该文件。原模板未改 |
| 原岗位和培训 | 三人并发执行本人既有任务，读取本人精确run；培训调用原知识/生成服务与持久结果，仅generate替换为合成函数。取消A不影响B/C，撤权A后B/C仍可操作 |
| 幂等与绑定 | 两个独立消费者竞争同事件，只写一次、触发一次、回复一次。绑定变化或调店后重放旧事件返回冲突，不迁移原业务归属、不在新店重新入账。这里是同进程独立连接，未声称多进程整链负载 |
| 群保护与伪造 | group文本、任务、培训及卡片均拒绝；账本、任务、SDK发送/上传、生成及工件零副作用。伪造其他成员或点击他人卡片不能授权。群聊功能没有开放 |
| Web兼容 | 实际调用原opening HTTP Request合同与共享授权库；原ManagerStore服务产生250元报告，企微按同编号查回、更正为200元后原汇总仍是一笔。覆盖无source和旧wecom-employee source |
| 关闭Web与重开 | 禁用全部合成Web接口，重开账本/工件/Bot后查回原报告、汇总和同字节文件，Web调用数不变。旧Web开通合同撤权/调店后Bot拒绝且报告/outbox行不变；恢复原门店后可读旧事实，无岗位重装 |
| 重启证据 | 上一行是同进程重开；另实际执行原report/delivery/operations/tasks独立进程示例，验证入账、blocked恢复、unknown不重投、同版文件、任务结果与取消记录按原编号查回 |
| 跨进程授权锁 | 子进程实际持有SQLite写锁，父进程等待后复核已提交的撤权，业务回调为零；等锁耗尽预算同样零业务回调。同步锁等待可能超截止时间，这证明过期后不写，不证明硬延迟上限 |

原完整manager网页/HTTP路由不在公开仓库，因此Web项仅为原开通Request合同及业务服务兼容，不是原Web页面E2E。原账号、岗位、账本、知识、记忆及完整页面继续保留，没有复制真实库或创建新账本替代原库。

## 性能观察

`npm run benchmark:local`先构建再运行脚本。最终样本环境：Windows x64、Node.js 24.18.0、12逻辑CPU；4个固定成员读取器/授权与单聊入口，同一个Node事件循环，共享临时SQLite和工件目录。每类首用1、暖身2、热串行20、并发20（5批各4人），共129条三步流水线、387次handle，0错误。每条handle预算4000ms，合成sender超时1000ms。所有耗时单位为毫秒，百分位用nearest-rank。
