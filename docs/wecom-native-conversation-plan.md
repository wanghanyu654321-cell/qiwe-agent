# 企微接入原 Agent 会话与多技能执行：最小改造计划

> 执行者按 `executing-plans` 逐项实施；每项运行行为先做失败测试，再实现、验证和独立审查。本文保留 D0 设计基线；2026-10-21 开始实施 D1 岗位空间与会话选择，本地证据见 [D1 验收记录](d1-acceptance.md)。D2–D5 自然语言执行、追问、取消及结果关联仍是计划，不能视为已接通。

**目标：** 员工在企微提出自然语言需求，连续追问，由原 Agent 使用获准岗位、技能和工具完成工作，结果持久保存、回复并可在企微查回或取消。

**技术栈：** 现有 TypeScript、SQLite、企微 SDK 1.0.7、Native host/container runner；不增加运行框架或依赖。

## 2. 员工目标体验与路由边界

以下是**完整目标交互**：D1 仅实现第 2 项及 `岗位查询`、`退出岗位对话` 的隔离接线；第 1 项仍需真实装配验证，第 3–5 项不是当前可用命令：

1. 管理员沿用统一开通，选择员工、门店、岗位。服务端准备并验证对应原账号、Profile、非 Home 工作空间。员工无需安装技能。
2. 员工发送 `岗位 内容营销`，机器人显示当前门店、岗位和会话。岗位名只用于选择，真实权限来自服务器绑定与当前授权。
3. 员工说：“按本周已审核活动写三条朋友圈文案，不要编价格。”先收到持久受理号，再收到原 Agent 的草稿或明确失败。
4. 员工继续说：“第二条口语一点，活动条件别删。”关联同一岗位会话和之前结果；执行中追问默认沿用原排队机制，不另开平行 Agent。
5. `查询对话 <受理号>` 查原持久状态及相应结果版本；`取消对话 <受理号>` 只作用于该输入对应的排队/活动执行。重启后仍能查回。

路由顺序：先识别岗位选择、对话查询/取消；再处理原有明确任务、培训、经营命令；最后按持久会话模式处理普通文本。有岗位对话时普通文本进入原 Agent；未选择岗位对话时保留原报数回退。新增明确 `报数 <原报数文本>` 入口，让对话模式中也能调用原报数处理器；`退出岗位对话` 恢复原普通文本规则。切换成功必须告知模式，避免同一句话悄悄写入不同系统；无经营权限时仍不能报数。新命令必须与现有解析器做冲突测试。

岗位切换只改变后续输入的目标。先前已受理的输入、结果和通知仍绑定原岗位/门店；切换不搬迁历史、不自动取消旧执行。权限撤销另行处理。首次仅支持单聊文字和已有确认卡片；保留出站 Excel、原 Web 附件/管理功能，入站图片、语音和文件另验收，不借本次扩成媒体工程。

## 3. 三个最小接缝的合同（拟新增）

### 3.1 可信岗位会话选择

- 扩展 Q 原开通端口，按本人 owner、门店、岗位查找并核验非 Home 空间及 Profile；不存在才按原空间创建规则执行。多个候选不能自动挑第一个，交管理员确认绑定。复用空间还要验证门店、原消息/记忆作用域和已有渠道绑定；仅 owner/Profile 匹配不足以证明空间适用于该门店。
- 当前 Q `/prepare` 和 N `POST /api/groups` 都针对当前登录者，后者按 `authUser.id` 检查 Profile 并设置 `created_by`，不是管理员代建员工空间接口。最小方案是管理员授予原 grant，员工第一次可信企微岗位选择时，由内部服务用经核实的本人上下文自动准备；员工不另装技能或登录 Web。提取原创建服务时保留 owner 的额度、权限、锁和审计，并记录企微来源。管理员只查看准备状态，不把 admin Cookie 传入员工链，也不增加任意指定 owner 的公网接口。
- 沿用原安装对账机制的原则：创建结果未知先按稳定标识查回，不盲目重复创建。原额度、空间权限、执行模式限制仍有效；不能拿管理员身份伪造员工创建请求。
- 在现有企微持久状态文件中增补会话选择记录：企业/机器人/成员、原账号、门店、岗位、授权与绑定版本、workspace JID/Profile ID、会话代次。只存引用，不复制技能、记忆、SDK 会话内容或密钥；不另建数据库服务。
- 每次受理、实际启动、工具业务写入及结果发送按其边界重新检查当前授权。旧输入重投仍使用原绑定快照；不因员工调店而重解释为新门店任务。
- 空间的 owner、门店、岗位归属固定，不能把有旧历史的空间改绑给新门店；原 Profile 重置不会清空该 JID 的历史。同一个空间的 Web 与企微使用原主会话和空间记忆，可能合批，这是复用的明确体验边界，不宣传渠道之间上下文隔离。需要不同作用域就选择已有匹配空间或创建新的非 Home 空间，不能靠提示词隔离。
- Profile 的原身份哈希和 session 重置机制继续生效。Q 授权变化不等于 Native 自动停止旧执行，需在接缝中联动停止/围栏；原 SDK 的 `bypassPermissions` 不能充当业务授权检查。

### 3.2 原宿主持久消息入口

拟新增内部端口仅在原宿主进程绑定，职责如下，**这些名称不是现有导出**：

```ts
// actor/target 由可信读取器生成并再次核验，不能从企微文本直接反序列化获得。
submitConversationMessage({ origin, actor, target, text }): Promise<Receipt>
readConversationReceipt({ actor, receiptId }): Promise<ReceiptWithResults>
cancelConversationReceipt({ actor, receiptId }): Promise<CancelOutcome>
// origin = corpId + botId + memberId + messageId；附固定 payload 指纹。
// target = 原 workspace JID、Profile、岗位/门店、授权版本及会话代次。
// Receipt 是持久受理事实；运行后再关联真实 query/turn 和输出消息 ID。
```

这是职责草案，实施时按原具体类型定义窄接口，不按此伪代码直接生成外部 API。通过提取原 Web 入站流程的渠道无关部分接入，Web 的身份与空间权限校验保持原位；原消息序列、游标、session 与历史拼接继续由原宿主管理。

持久去重是必要改动：N `storeMessageDirect` 使用 `INSERT OR REPLACE`，仅使用确定性 messageId 会覆盖冲突载荷，不能保证恰好受理一次。计划在原 Native SQLite 增补渠道受理关联表，以 origin 唯一约束保存指纹、固定归属、原输入 messageId、执行/输出关联和取消意图；与原输入保存使用同一连接事务。不同载荷复用 origin 必须拒绝。先核实原事务嵌套和游标选择规则，不能直接套一层事务破坏原行为。

Q 的状态库与 Native 库不是一个事务：Native 提交而 Q 回执丢失时，应按 origin 向 Native 查回；无法确定就返回未知并停止重投执行。Native 已提交但尚未入队的记录，恢复后在原门禁允许时补入原队列。新增表和补偿入口必须纳入 T7 扫描/恢复覆盖，不能成为另一套维护期收件箱；门禁关闭时不持久承诺新业务受理。

输入可能合批，queryId、turnId、SDK sessionId、scheduler task runId 不可混用。受理表保存实际调度时的输入集合和运行关系，输出引用原消息及下述冻结版本，不维护另一份可变“最终答案”。同批多个输入可关联同一输出，但不能跨账号/空间。

原 `processGroupMessages` 按整个 chatJid 拉未消费输入；因此启动前还需逐条重验企微输入的固定归属与授权版本，失效输入不能随着同空间的新输入一起执行，不同企微授权版本不得合批。Web输入保持原授权规则，不伪造企微来源；混合批次记录所有输入来源，通知只发给有合法关联的企微受理者。若已开始的混合执行因企微撤权必须停止，原Web也可能观察到本次执行被中断，应如实展示；不能承诺只从运行中的模型上下文删除某一句。该兼容影响在D3单独验收。

取消按真实状态处理：未启动只取消目标输入；活动输入用确切 JID 和 expectedQueryId；已结束返回原终态。实现前核实原消息选择/游标是否能排除已取消输入；若不能，增加仅针对渠道受理记录的持久取消过滤，并验证不跳过同批其他输入。合批后单条输入已进入同一执行时，需告知取消会停止该次共同执行，不伪称能撤回其中一句；保留其余未执行输入。`interruptQuery` 返回成功只证明写出中断信号，必须等原 runner 终态才能标已取消；所有已进入同一批次的受理号关联同一执行终态。断连/崩溃时保留取消处理中或未知，不能自动重跑该批中其他已进入执行的输入。迟到取消不得中断下一轮，已产生业务副作用不自动回滚。

### 3.3 持久输出转企微回复

- 原 runner 确认执行终态后，按受理关联和当前权限生成结果通知；checkpoint/续写不是最终完成。N `db.ts:2699–2712` 的 `sdk_final/truncation_continue` 可能复用同一消息ID并覆盖内容，不能把输出ID当不可变版本。计划在 Native 同库受理关联中追加终态结果快照：源输出ID、实际执行身份、递增修订号、内容摘要及该版本内容，和终态记录同事务写入；这是原结果的不可变查回证据，不新建结果数据库/生成服务。重复完成回调按执行身份和摘要幂等，后续修订另增版本，不能改旧快照。企微通知固定该版本，查询可同时标明当时版本及最新版本。
- 复用 Q `wecom-bot-sender.ts` 的发送端口、`manager-store.ts` 既有回复意图 reserve/prepare/claim/finish 及文件能力。通知键包含受理/结果版本、原收件人和渠道，prepare 固定载荷，不在重试时读取会变化的最新回答。
- 当前 `wecom-bot-delivery.ts` 的构造和恢复仍围绕报告；需要抽出窄的共用投递接缝/扩展结果类型，不能假造报告或要求内容营销员工拥有经营权限。入账提示文案不能用于 Agent 输出。
- 4 秒入站预算只管理当前身份读取与受理响应，不覆盖整个 Agent 执行；不复用已过期 req_id、已关闭的请求作用域或旧权限。长时结果用现有主动发送能力，能力不可用时持久记录失败并提供查回。
- 通知固定原收件人与输出 ID/版本，发送前复核权限。业务已完成、通知失败、投递未知分别保存；未知不盲重发。Native结果完成与Q创建通知意图也是跨库间隙：在原门禁允许的启动/恢复或主动查询入口，按已完成受理与冻结版本有限枚举，幂等补建缺失意图；不能重跑Agent来补通知，不能覆盖已存在的投递未知记录，不另建常驻调度服务。
- 状态至少区分已受理/排队、执行中、取消处理中、已取消、完成、失败、执行结果未知；通知状态独立。执行中只展示真实阶段，不能凭空给进度百分比。

## 5. 验收不能只剩报数

| 验收线 | 必须证明 | 禁止替代 |
| --- | --- | --- |
| 报数基础链 | 原账本一次入账、回复、重启查回，旧更正/汇总/Excel不回归 | 只看到HTTP成功 |
| 岗位对话链 | 可信岗位 → 原消息 → 原会话执行 → 持久输出 → 企微回复；同空间连续追问，跨岗/跨店隔离 | 新建固定别名任务模拟自由对话 |
| 多技能链 | 首选内容营销草稿：用隔离已审核活动资料与已有技能完成草稿及修订，至少覆盖两个可核实的能力步骤 | 仅打印两个技能名称；将两个独立suite当成同请求 |
| 故障与安全链 | 无资料、权限撤销、Profile失配、模型不可用、工具失败、崩溃、发送未知、迟到取消均给出真实状态；不虚构价格/成功/发布 | 全部拒绝也算正常能力通过 |

内容营销只是第一条多技能验收，不删除店长分析、质检、培训等能力。具体技能 ID 必须来自原安装清单和文件证据；找不到所需技能就如实记录缺失，不凭岗位名新造同名技能。培训专用入口继续保留原审批、暂停与额度约束；通过通用对话也不能绕过这些服务门禁。草稿不自动发布，任意高副作用 MCP/终端工具不因企微接入扩大权限。

本地零模型只能证明输入、上下文、技能装配、工具调用及持久状态连接；脚本化模型响应不能证明真实模型会理解自然语言并自主选择正确技能。真实语义质量、企微手机实收与生产可用必须在后续取得相应授权后独立验收。

## 6. 对 T7 恢复的精确影响及回退

T7-A仍负责全宿主恢复：非数据库残留、外部写者、写者覆盖、不透明运行元数据四类证明及逐记录处置，没有一项因新增渠道而豁免。对话新增的受理表、取消意图、Profile/空间准备、原 runner/工具、结果补投都要进入 A1 有限清单，A2验证真实状态/围栏，A3经原 review/restore 放行。Linux承担正向恢复；Windows继续验证启动和原扫描器失败关闭，不顺手移植扫描器。

侵入度判断：**纯企微路由较低；原入站事务、输入执行关联、取消和恢复覆盖为中等，是必要侵入点。** 不是“加一个机器人接口即可”，但无需重写 Agent、原账本或页面。先提取窄接缝并以原 Web 回归保护，避免重构整个 `web.ts/index.ts`。

新字段/表采用增量迁移，旧任务引用格式保持可读；不更名旧状态、不把 scheduler run 改成 query。回退时先停止新对话受理，按原规则处置在途执行和通知，再卸下新路由；保留受理与结果关联数据供查回/审计。旧版本不认识的新记录不得当作待重试任务，新表纳入恢复检查后不能直接降级到忽略该表的旧宿主。不得删表、删账号、清记忆或回滚业务结果换取“恢复成功”。
