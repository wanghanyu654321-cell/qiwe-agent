# Agent Claw 企微多技能员工：产品使用说明与工程对应

日期：2026-10-21。核对运行源码基线：`7b69a13`。这是一份目标使用说明和现状对照，不是已上线功能承诺。本文的“目标示例”不能当作当前可输入命令。

## 产品最终应该是什么

员工在企微找到门店的 Agent Claw，使用自己获准的岗位能力，把工作交给原 Agent：查经营数据、做营销草稿、分析材料、学习门店知识，以及查询或取消任务。管理员在原 Web 开通员工、门店和岗位，管理知识、技能、模型配置与审计。员工日常操作和结果查回在企微完成。

岗位是工作职责与权限，技能是完成工作的方法和工具。开通“内容营销”不等于自动允许发布；能生成建议不等于有权改账、发消息或操作外部系统。继续使用原 Agent 运行循环和原业务服务，不为每个岗位重建一套 Agent、账本或账号。

**报数是第一条打通的验收链，不是产品最终形态。** 最终交付还要证明员工能完成至少一个真实岗位任务，并在同一任务上下文中追问、查回和取消。哪些技能可用，来自原配置、权限和实际运行证据，不根据岗位名称推定。

## 一名美容门店员工的一天

以下人名、门店和内容均为示例。

### 1. 店长开通使用

目标体验：管理员为“小林”选择B店及内容营销、培训等岗位。小林进入企微后只能使用获准能力；调店、停用或撤权后，旧消息和旧任务不能继续取得新权限。管理员完成已有装配，员工无需再安装技能或重新配置模型。

已有基础：原Web统一授权与企微读取同一授权事实，本地验证了开通、撤权、绑定变化和门店隔离。差距：真实企微成员绑定与宿主装配尚未验收；当前固定任务还需要服务端已有任务目录，不能把“开通岗位”宣称为所有技能已经可执行。员工可见的能力列表/选择交互也不能仅凭后台已有岗位配置判定完成。

### 2. 下班报数

已有命令示例：`今天销售成交88.88元`。目标是返回期间、金额和报告编号，员工核对后确认，才进入原账本；再发 `查询 实际报告编号` 查回。同一条消息或确认重复到达，不重复累计。金额沿用销售成交口径，不冒充实收、充值或余额消耗。

现状：解析、账本、确认、去重、通知与查回有本地隔离验证，真实机器人闭环未验收。此链不需要新增模型调用，适合先验证产品从输入到持久结果再到回复是否可靠。

### 3. 请内容营销岗位协助工作

**目标示例，尚未支持直接这样使用：** “按B店本周已审核活动，写三条适合企微朋友圈的文案，不要编造价格。”随后追问：“第二条改得更口语一点，保留活动条件。”

目标结果：原Agent使用获准资料与技能生成可查回的草稿，说明依据和缺失信息；后一句关联同一任务和结果版本。缺少已审核活动资料时询问或说明无法确认；没有发布授权就只交付草稿。

目前能表达的是 `执行任务 内容营销 weekly` 这类固定命令，且 `weekly` 只是示例别名，必须已经在服务端配置并映射到本人获准的原任务。它不携带任意自然语言任务参数，也不能代表“改第二条”的连续对话。真实Native执行仍未启用。

特别注意：当前不匹配任务/经营命令的普通文本会进入报数解析，可能得到缺少报数信息的提示，并不是交给通用Agent回答。入站仅装配文字和指定确认卡片；图片、语音、文件发起任务尚未接入。已有Excel上传/发送属于出站能力，不能据此推定机器人可以读取员工附件。

所缺工程：可信岗位会话路由、原Agent接受用户需求的适配、任务与对话引用、追问/结果版本关系、原技能及工具权限接线、持久输出与企微回复。必须先核实原入口；不能绕开原Home/Profile限制，也不能新开第二套执行循环。

### 4. 培训和其他岗位

已有格式示例：`培训问答 指导员 如何做好顾客家访`，或 `培训教案 总指导 新员工接待训练`。目标是按已批准资料输出有来源、可查回的答案/教案；资料过期、无证据或生成失败时明确说明。当前生成端口只做合成验证，真实生成仍受原暂停、额度及后续模型授权约束。

店长经营、投放辅助、质检等也要按“具体输入 → 原服务/技能 → 有依据的结果 → 保存与回复”逐项验收。当前有岗位键和任务路由，不等于每个岗位的完整业务技能都已接通。

### 5. 查询、取消和异常

已有格式：`查询任务 岗位 实际任务编号 [页码]`、`取消任务 岗位 实际任务编号`。目标是返回同一原任务的状态和结果；取消受理不等于已经停止，已发生的业务操作不因取消自动撤销。员工无需到Web查回。

入账成功但通知失败时，查询仍返回原入账事实；发送结果未知时不盲目再发。重启后查的是原持久记录。维护期当前没有可靠收件箱，不能承诺稍后自动处理；渠道断开时也不能保证即时回复，开放前需要验证可见的维护提示及恢复后查询步骤。

## 两条必须区分的完成线

**首条可用闭环：** 报数、确认、可信回复、异常处理及重启查回，在同一个恢复后的宿主上完成，再由真实企微验收。它验证基础交付链，不证明多技能员工完成。

**多技能员工可用：** 除首条闭环外，还需完成一个真实岗位的“提出需求 → 原Agent按当前授权调用原技能 → 保存有依据的结果 → 企微回复 → 同任务追问或修改 → 查询/取消/重启查回”；再将结果扩展到其余已承诺岗位。验证工具选择、资料不足、撤权、模型失败和工具失败，而不是只验证接口返回。

暂以内容营销草稿作为候选首个多技能场景，原因是能检验知识、技能、连续对话及结果版本，且可先停在草稿。具体原技能/会话入口未核实前不承诺已具备，也不在本轮自动新增自然语言调度方案。真实模型调用、消息和部署仍需要对应授权。

## 推进方式和当前信心边界

1. T7-A先核实并补原恢复必要契约；不拿新诊断计数替代恢复规则。
2. T7-B贯通首条报数回复链，T7-C完成回归和受控真实验收。
3. 与T7分开跟踪“多技能对话接线”：先核实原Agent会话/岗位/技能执行接口，再确定最小适配及验收，不把这一缺口藏在T7尾部。

有证据支持继续复用原系统，但目前没有依据保证仅补恢复门禁即可交付多技能员工，也无法承诺完整恢复的剩余工期。因此先把这份使用说明和T7-A规则清单交付给产品负责人；未确定的规则不靠猜测实现。已有功能和数据保留，不为展示进度另建账本、调度器或Agent内核。
