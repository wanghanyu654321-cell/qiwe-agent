**目标：** 员工在企微发起操作，收到与原持久业务状态一致的回复；异常有明确处理方式，重启后仍能在企微查回。

**架构：** 复用原授权、账本、通知状态、Agent 和单一执行循环；企微负责员工入口，原 Web 保留管理和审计。首条验收链固定为“报数 → 待核对摘要 → 本人确认 → 入账回复 → 独立进程重启后查回”。安全恢复是前置条件，不能切换宿主模式、删除限制或另建运行循环绕过。

**技术栈：** 现有 TypeScript、SQLite、企微 SDK 1.0.7、Native 宿主及 Windows/Linux 隔离验证工具，不新增依赖。

## 完成标准：看员工得到什么

| 场景 | 必须可观察的结果 |
| --- | --- |
| 员工报数 | 返回同一份已保存报告的编号、期间、金额与核对操作；缺项不允许确认，文本和卡片不能授予权限 |
| 本人确认 | 原事务只入账一次；回复明确已入账及报告编号；重复消息或确认不重复累计 |
| 已入账但回复失败 | 业务结果保留，通知失败或未知单独记录；新查询返回原报告事实，不重新执行报数 |
| 发送结果未知 | 不写成已送达，不盲重发；平台ACK、发送记录与手机收到分别验收 |
| 权限或门店变化 | 按当前原授权拒绝越权；旧消息重投不得在新门店生成第二笔业务 |
| 超时、维护或断线 | 不伪报成功；能安全回复时给出查询/稍后重试说明。渠道已断时不能保证即时提示，不能假定平台重投；真实开放前验收员工可见的维护提示与恢复后查询方式 |
| 重启后查询 | 第二个独立进程只读取第一轮持久数据，返回同一报告及真实入账状态，不靠内存或重建样例 |

本地闭环必须有同一请求经过SDK事件处理、可信身份、原门禁、原业务事务、原持久通知及回复载荷的组合证据。外发替身仅代替平台网络，检查实际载荷和收件人，不能只断言内部返回 handled。各模块分别通过不能拼成闭环通过。
