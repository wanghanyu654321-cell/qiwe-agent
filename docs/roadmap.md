# 员工企微产品可用闭环计划

> 执行者使用 executing-plans 按依赖推进；运行行为变更先做有效失败测试，交付前进行独立规格及质量审查。

**目标：** 员工在企微发起操作，收到与原持久业务状态一致的回复；异常有明确处理方式，重启后仍能在企微查回。

**完整产品目标：** 原Agent Claw成为员工在企微可使用的多岗位、多技能助手，参见[使用说明与工程对应](product-usage-and-engineering.md)。报数是第一条验收链，不是全部产品。当前固定任务别名不支持任意自然语言需求和连续追问；这项差距必须单独跟踪，不能以T7恢复通过代替多技能员工验收。

**架构：** 复用原授权、账本、通知状态、Agent 和单一执行循环；企微负责员工入口，原 Web 保留管理和审计。首条验收链固定为“报数 → 待核对摘要 → 本人确认 → 入账回复 → 独立进程重启后查回”。安全恢复是前置条件，不能切换宿主模式、删除限制或另建运行循环绕过。

**技术栈：** 现有 TypeScript、SQLite、企微 SDK 1.0.7、Native 宿主及 Windows/Linux 隔离验证工具，不新增依赖。

2026-10-21收紧计划；核实基线为 `7b69a136e1b1ccd221690eb75aa64a6c4db06c19`。本文件是当前执行顺序入口，既有验收文档保留为历史证据，不将已完成检查重复列为新交付。

## 当前事实与边界

- T0–T6已有本地隔离切片，涵盖身份、报数、更正、汇总、Excel、任务、培训接缝、多成员及兼容性；不能视为真实员工验收。
- T7已有真实SDK离线协议验证、Native定向执行及完整宿主启动/双进程重启验证；四类全局证明和逐记录处置仍未闭合，正常恢复未通过。详情见[上一轮证据](t7-recovery-evidence-acceptance.md)。
- 企微准备控制仍限于 `isolated-synthetic`，尚未接上实际主进程的真实渠道生命周期；维护期没有持久收件箱，不能承诺自动补收。
- 本地工作限于合成身份、临时数据、受控I/O；不动生产、不发真实消息、不新增模型调用，不读取真实数据库、密钥及配置。真实联调与发布各有单独授权边界。
- 首条链优先验收不等于删除其他功能。更正、汇总、Excel、岗位与培训代码保留并回归，其真实启用需要各自验收。群聊开放、任意提示词执行、通用多渠道改造不进入本次关键路径。
- 原Owner、岗位、非Home任务和精确run约束继续保留，不切换Home Profile或裸调用推进全库的trigger；原培训暂停/额度门禁保留。SQLite同步等待硬时限仍未实现，旧XML/Web调用方继续纳入相关兼容回归。

## 完成标准：看员工得到什么

| 场景 | 必须可观察的结果 |
| --- | --- |
| 员工报数 | 返回同一份已保存报告的编号、期间、金额与核对操作；缺项不允许确认，文本和卡片不能授予权限 |
| 本人确认 | 原事务只入账一次；回复明确已入账及报告编号；重复消息或确认不重复累计 |
| 已入账但回复失败 | 业务结果保留，通知失败或未知单独记录；新查询返回原报告事实，不重新执行报数 |
| 发送结果未知 | 不写成已送达，不盲重发；平台ACK、发送记录与手机收到分别验收 |
| 权限或门店变化 | 按当前原授权拒绝越权；旧消息重投不得在新门店生成第二笔业务 |
| 超时、维护或断线 | 不伪报成功；能安全回复时给出查询/稍后重试说明。渠道已断时不能保证即时提示，不能假定平台重投；真实开放前验收员工可见的维护提示与恢复后查询方式 |
| 重启后查询 | 第二个独立进程只读取第一轮持久数据，返回同一报告及真实入账状态，不靠内存或重建样例 |

本地闭环必须有同一请求经过SDK事件处理、可信身份、原门禁、原业务事务、原持久通知及回复载荷的组合证据。外发替身仅代替平台网络，检查实际载荷和收件人，不能只断言内部返回 handled。各模块分别通过不能拼成闭环通过。

## T7 收紧后的执行顺序

### T7-A：原宿主可安全恢复（当前主阻塞）

**边界：** 只补当前候选宿主恢复所需的真实证据生产者、记录处置和原门禁接线，不建设通用证明平台或新管理页面。四项证明仍按原门禁完整作用域判断，不能只检查报数表。未启用能力只有通过原有控制明确停用并证明隔离后才能不执行；代码保留、无流量或本进程计数为零都不是隔离证明。

**接点：** `integrations/native/full-host-candidate.mjs`、`integrations/native/full-host.test.mts`，以及原 `appointment-boot-inventory.ts`、原 gate 和消费者。原源码只读，必要变更在既有候选转换边界实施。`recovery-inspection.ts` 只消费诊断结果，不能自行签发许可。

- [ ] A1：在既有恢复验收文档建立有限清单：每项阻塞及逐记录 blocked 分类对应的原读/写入口、事实来源、处置规则、行为反例、是否需要外部证据。全局要求超出报数场景的部分明确列为共同前置条件，不静默缩小作用域。
- [ ] A2：每次选一个确定契约，先用合成未结束记录或仍有写能力的执行者证明拒绝，再实现原规则允许的处置/围栏。成功来自真实状态变化和原扫描结果，禁止注入 safe/ready、删除 blocker 或使用空库。
- [ ] A3：必要前置满足后，经原 review/restore 路径恢复完整候选宿主，验证供B使用的同一宿主实际进入可受理状态；证明恢复过程不会复活已取消任务、误发旧通知或重复入账。无法解释的记录继续阻断。
- [ ] A4：Linux验证正向恢复、恢复后运行及双进程重启；Windows验证启动、原驱动和失败关闭路径。原安全文件扫描当前只支持Linux，不把Windows拒绝当作待删除的障碍，也不默认新增跨平台扫描移植。真实旧执行者/Provider证明单列“待受控核实”，本地合成不能替代。

2026-10-21核实进展：已完成原放行次序、处置分组、缺失生产者及平台限制调查，见[恢复规则与证据来源](t7-recovery-evidence-acceptance.md)。逐表/逐入口协议尚未全部核实，A1保持未完成；本轮按用户要求优先交付产品使用说明，不实施猜测性的A2放行代码。下一步先界定旧写者失权的原协议，再实现有原业务依据的局部分类。

**退出条件：** 本地原恢复路径及恢复后业务准入证据成立，供B复用同一运行宿主；真实环境所需核实项有具体采集方法和停止条件。不能只把四项状态改成通过。A1发现原业务规则缺失时，停止依赖该规则的实现，说明具体缺口，不用外围计数替代。

### T7-B：操作、回复与查回贯通

**复用接点：** `src/role-eval/wecom-bot-preparation.ts`、`wecom-bot-assembly.ts`、`wecom-bot-handler.ts`、`wecom-bot-delivery.ts`、`manager-store.ts`。测试复用 `integrations/native/bot-preparation-native.test.mts`、`full-host.test.mts` 及 `tests/role-eval/wecom-bot-assembly.test.ts`、`wecom-bot-delivery.test.ts`、`manager-bot-delivery-store.test.ts`。只修改组合场景暴露的缺口，不重建授权、账本或发送服务。

- [ ] B1：在恢复后的同一候选宿主装配原渠道执行边界，贯通报数、确认、入账回复和新查询，核对文本/卡片载荷、报告编号、收件人及持久结果。
- [ ] B2：验证提交后断线、发送超时/未知、重复投递、读取中撤权、跨门店、维护期入站；业务和通知分离，不重复执行。明确未发送才按原规则恢复，未知投递通过新查询处理。
- [ ] B3：第二进程从持久数据查回同一报告并保留通知状态；维护期间没有持久受理的消息不能声称自动补办。
- [ ] B4：在可发送/不可发送两种状态验收维护说明与恢复步骤，不默认新建持久收件系统。

**退出条件：** 上表首条链场景具有同版本组合证据，正常回复与失败处理都可用。B的夹具准备可以提前进行，但A未通过时不能把替身宿主测试标为完整闭环完成。

### T7-C：既有功能回归与受控真实联调

- [ ] C1：回归更正、汇总、Excel、任务查询/取消、培训接缝及原Web授权调用方；分别标明已启用、保留未装配、暂停，不用报数成功代表全部功能上线。
- [ ] C2：独立审查最终规格与代码，核对门禁、权限、数据一致性、异常恢复和升级影响。只读诊断增量不能替代A/B退出条件。
- [ ] C3：本地条件满足后提交具体真实联调清单：一个已授权测试成员和门店、测试数据标识、限定动作、有限真实发送、原执行者核实、停止条件及回退。获得对应授权后再验证手机实收、报告查回、平台行为及维护提示；当前不执行。
- [ ] C4：岗位Agent和培训真实生成另列有限模型评测及预算授权；生产部署另核对制品、配置与回退。首条无模型报数闭环不等于Agent生成能力恢复。

**退出条件：** “本地闭环通过”“真实企微验收通过”“已部署”分别登记。只有员工在真实企微完成操作、收到对应结果并查回，才称首条产品闭环可用；整体T7仍需完成其他约定能力联调和发布条件。

## 验证与变更控制

多技能对话接线与T7-A恢复工程分别跟踪：核实原Agent消息/会话入口、可信岗位与Profile路由、技能/工具授权、任务输入和输出引用；确定契约后再做最小适配。当前只做使用说明与源码核对，不自动新增自由对话调度实现。内容营销草稿可作为首个候选验收场景，具体原能力未核实前不承诺上线或日期。

每次运行行为修改先执行相关测试，再运行仓库真实脚本 `npm test`、`npm run typecheck`、`npm run build`。涉及宿主时执行 `integrations/native/verify-full-host.mjs` 的现有双进程验证及受控Linux验证，原源码/驱动路径从当前环境核实，不复制旧结果。结论绑定当前版本和日志。纯计划修改仅检查内容、相对链接及 `git diff --check`，不编造业务测试。

新增改动必须说明解除哪个A/B阻塞或保护哪个已有行为。需要新增调度器、数据库、通用证明框架、维护收件系统或重构业务模块时，先说明原能力不足和新增范围，不自动纳入。不得删除 `isolated-synthetic` 检查充当生产接线。

原15–20人日、含缓冲18–24工作日估算基于尚未识别全部恢复缺口的范围，停止用作当前剩余工期依据。完成A1后按确定的证据生产者与处置工作重新估算；外部核实和真实验收等待单列，不承诺未经核实的上线日期。
