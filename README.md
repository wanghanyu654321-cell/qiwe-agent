# qiwe-agent

企微员工入口接入现有 Agent 与门店业务服务。本仓库当前交付 **T0–T3 本地隔离切片**：复用原账号、门店、岗位授权和经营账本，验证文字报数、卡片核对、同一报告查回，以及结果回传、失败恢复和投递去重。

## 当前可以验证什么

- 企微成员通过显式服务端绑定关联原账号，不使用管理员 Cookie。
- Web 与企微读取同一份 `WorkbenchAccessStore` 授权；原 Web 管理员开通或撤权后，企微侧同步按当前记录判断。
- 从配置的 Native SQLite 只读查询最小账号状态及本人唯一 Home，不初始化原数据库、不创建岗位、不返回密码字段。
- 检查停用、强制改密、门店/岗位撤权、绑定变更、来源异常、取消与超时；迟到结果不会恢复权限。
- 上下文由本进程工厂登记，复制或伪造的 JSON 不能直接作为执行权限。
- 复用原离线报数解析与SQLite账本，金额使用整数分，保留原期间、快照、新增及更正规则；T2只接收报数、本人确认与单条查询。
- 同一消息重放、重复确认不会重复累计；确认使用已保存的候选项，卡片参数不能修改金额或员工归属。
- 重开数据库或启动新进程后，可用原报告编号查回真实入账状态。确认事务保留原`prepared`通知意图，T3通过显式合成SDK端口验证投递及回执。
- 发送前持久化`attempting`；明确未发送的`blocked`可受控恢复，`unknown/attempting`不盲重发。新查询单独回复，不把原未知通知改成成功。
- 平台事件指纹和回调路由在业务前保留；冲突重放不会先入账再报错。即时确认回复与恢复通知竞争同一条原持久记录，避免双发。

当前入口限制为 `isolated-synthetic`，企微事件及SDK方法以显式本进程合成端口注入。**尚未连接真实机器人、发送真实消息或运行原 Agent。** 员工操作和查回使用企微消息/卡片载荷，Web继续承担原管理、数据流转与审计。T3合成ACK只验证本地处理，不能视为真实平台受理或手机实收。

## 美容门店场景

已获原`manager`经营岗位授权的美容师发送“今天销售成交88.88元”，系统保存待核对报告并返回期间、金额和确认按钮。本人确认后，原账本记入8888分；再发“查询 报告编号”查回同一条结果。未获该岗位授权的员工不会自动升权。

缺少日期、金额等必要内容时只保留待核对结果，不提供确认按钮。重复消息、已存在的期间冲突、失效卡片及越权请求都有明确处理；更正、汇总和Excel的企微入口在T4接入。销售成交额沿用原口径，不等同收款、充值或余额。

## 本地运行

需要 Node.js 22.13 或更新版本。当前本地验证环境为 Node.js 24.18.0。

```bash
npm ci --ignore-scripts
npm test
npm run typecheck
npm run build
npm run demo
npm run demo:report
npm run demo:delivery
```

演示只使用系统临时目录中的合成数据库。`demo`验证开通与撤权；`demo:report`验证报数、确认和新进程查回；`demo:delivery`验证断线后新进程恢复一次、再次启动零重发，以及未知结果不重发但新查询可用。不读取本人实际数据库，不连接企微或模型。

## 文件职责

| 文件 | 职责 |
| --- | --- |
| `workbench-access.ts` | 复用原门店/岗位授权持久化与版本控制 |
| `workbench-authority.ts` | Web/企微共享的当前授权检查 |
| `workbench-opening.ts` | 保留原 Web 开通、本人读取与岗位准备流程 |
| `wecom-bot-bindings.ts` | 严格读取服务端成员绑定，不接受额外权限字段 |
| `wecom-bot-context.ts` | 可信身份接线、上下文登记、重新核验、预算与取消 |
| `native-bot-identity.ts` | 按现有 Native schema 只读查询账号及本人唯一容器工作间 |
| `manager-report.ts` / `manager-store.ts` | 原经营解析与单一账本，兼容XML/Web及独立机器人来源 |
| `wecom-bot-handler.ts` / `wecom-bot-transport.ts` | 可信事件与授权匹配、报数/本人确认/查询、官方形状回复计划 |
| `wecom-bot-sender.ts` / `wecom-bot-delivery.ts` | 合成SDK发送、原持久通知状态、业务前事件排重、恢复及未知结果处理 |
| `install.ts` / `file-journal.ts` / `workspace-access.ts` | 原开通流程依赖，保持原能力与测试兼容 |

源码均位于 `src/role-eval/`。绑定与Native读取依赖是服务端端口；未来 SDK/内部进程装配必须验证调用者，不能把客户端字段、HTTP Header 或反序列化上下文当权限。

## 验证与边界

本切片使用真实临时 SQLite、合成绑定及可控延迟进行验证。`withCurrent()`只串行化原授权库的同步提交，不能保证 Native、绑定与业务多库原子撤权。执行/写入和敏感结果返回前仍须在后续调用方重新核验。

T0发现原固定B店与统一开通的账本路径、作用域不同。T2显式注入已有`ManagerStore`、原scope和账号→原员工映射；同一SQLite文件内全局来源去重。真实装配前必须确认原库路径，不能自动切换为空库，也不承诺不同文件间全局去重。本次没有迁移、复制或重建实际经营账本、历史、知识和记忆。

T3在原SQLite文件增加`bot_reply_intents`回复元数据表，记录事件预留、回复计划与投递状态；原`employee_reports`及业务口径保留。主动恢复仅向原成员发送，API `recover`是受控服务端入口，查询不会隐式触发重发；没有新增公网路由、员工重试命令或后台循环。
